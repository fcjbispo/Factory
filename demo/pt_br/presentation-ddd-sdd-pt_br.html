02 / 10 Domain-Driven Design

O que é DDD?

Domain-Driven Design é uma abordagem de desenvolvimento de software criada por Eric Evans (2003) que coloca o domínio do negócio no centro do design.

"O mais importante em um software não é seu código, nem sua arquitetura — é o problema de negócio que ele se propõe a resolver."

O DDD não é um framework ou tecnologia — é um conjunto de princípios e padrões que guiam a modelagem de sistemas complexos, garantindo que o código reflita fielmente a realidade do negócio.

🎯

Objetivo Principal

Criar sistemas cujo design espelha o domínio, facilitando evolução, manutenção e comunicação entre stakeholders.

🤝

Colaboração Intensa

Desenvolvedores e especialistas de negócio trabalham juntos para construir um modelo compartilhado do domínio.

🔄

Modelagem Contínua

O modelo evolui constantemente com base no feedback do negócio, mantendo-se sempre alinhado à realidade.

03 / 10 DDD – Pilares Fundamentais

Os Três Pilares do DDD

🗣️

Linguagem Ubíqua

Vocabulário comum e consistente usado por toda a equipe — devs, gerentes, especialistas. Nomes no código, documentação e APIs usam os mesmos termos.

Ex: Sempre "Pedido", nunca "Order" ou "Compra"

📦

Bounded Context

Fronteira explícita onde um modelo de domínio específico se aplica. Cada contexto é dono dos seus próprios dados e tem sua própria linguagem ubíqua.

Ex: "Cliente" no Contexto de Vendas ≠ "Cliente" no Financeiro

🗺️

Context Map

Mapa que mostra como os Bounded Contexts se relacionam entre si. Define padrões de integração: Partnership, Customer/Supplier, Anti-Corruption Layer, etc.

Ex: ACL protege seu contexto de modelos externos

04 / 10 DDD – Estratégico & Tático

Design Estratégico vs. Design Tático

🧭 Design Estratégico

Nível MACRO — visão do negócio e estrutura geral

Entender profundamente o negócio e subdomínios
Delimitar Bounded Contexts
Definir Context Map (relacionamentos entre contextos)
Estabelecer a Linguagem Ubíqua
Organizar fronteiras e integrações

🔧 Design Tático

Nível MICRO — implementação dentro de cada Bounded Context

Entidades: objetos com identidade única (ex: Pedido #123)
Value Objects: imutáveis, definidos por atributos (ex: CPF, Endereço)
Agregados: unidade de consistência com raiz (Aggregate Root)
Repositórios: abstração para persistência de agregados
Domain Events: eventos que disparam ações entre contextos

06 / 10 Spec-Driven Development

O que é SDD?

Spec-Driven Development é o processo de definir contratos formais (specs) para cada Bounded Context. Em vez de documentar funcionalidades soltas, você define especificações que servem como contrato de API.

Cada Bounded Context tem sua própria spec — um contrato de API separado por contexto que formaliza a comunicação entre as partes do sistema.

Contratos claros e testáveis entre contextos
Comunicação formalizada e versionada
Nomes da spec refletem o domínio (Linguagem Ubíqua)
📝

Spec = Contrato

A especificação define exatamente o que cada contexto expõe e espera receber — como uma interface legal entre times.

🔒

Isolamento Garantido

Cada contexto evolui independentemente. Mudanças internas não quebram outros contextos — desde que a spec seja respeitada.

🤖

AI-Ready

Specs formais permitem que agentes de IA entendam e interajam com o sistema de forma precisa e previsível.

08 / 10 Framework Factory

A Integração: DDD + SDD

O Framework Factory integra as duas metodologias para criar uma governança completa de projetos de software.

🧠 DDD

Define COMO o sistema é organizado

Bounded Contexts como fronteiras de domínio
Linguagem Ubíqua como vocabulário comum
Agregados, Entidades e Value Objects
Context Map para relacionamentos

📋 SDD

Define O QUE cada parte expõe

Contratos de API por Bounded Context
Nomes da spec = Linguagem Ubíqua
Documentação derivada de templates
Agentes de IA como cidadãos de primeira classe

Princípios Fundamentais: Documentação deriva de templates → Cada Bounded Context tem sua spec → Linguagem Ubíqua é contrato → Agentes de IA são cidadãos de primeira classe

09 / 10 Casos de Uso

Quando Usar DDD + SDD?

✅ RECOMENDADO PARA

Sistemas complexos com regras de negócio elaboradas
Projetos de longo prazo com evolução contínua
Domínios com múltiplos stakeholders e linguagens distintas
Migração de legado onde o domínio precisa ser redescoberto
Microsserviços — cada Bounded Context mapeia para um serviço
Times distribuídos que precisam de contratos claros

❌ NÃO NECESSÁRIO PARA

CRUDs simples sem regras de negócio complexas
Protótipos e MVPs de curta duração
Sistemas com domínio trivial ou bem compreendido
Projetos solo sem múltiplos times
Sistemas estáveis com pouca evolução prevista
10 / 10 Resumo Executivo

Por que DDD + SDD importam para o Negócio?

💰

Redução de Custos

Menos retrabalho por mal-entendidos. Mudanças são localizadas em Bounded Contexts, sem efeito cascata no sistema todo.

⏱️

Time-to-Market

Times trabalham em paralelo com contratos claros (SDD). Cada contexto evolui independentemente, acelerando entregas.

🛡️

Mitigação de Risco

Contratos formais (specs) eliminam ambiguidades. A Linguagem Ubíqua garante que todos falem a mesma língua.

📈

Escalabilidade

Bounded Contexts viram microsserviços naturalmente. O sistema cresce de forma organizada e sustentável.

🧩

Manutenibilidade

Código que espelha o negócio é mais fácil de entender, modificar e testar. Onboarding de novos devs é mais rápido.

🤖

AI-Native

Specs formais + Linguagem Ubíqua permitem que agentes de IA contribuam com precisão, acelerando o desenvolvimento.
