O Que É a Factory?

Definição e Propósito

A Factory é o framework de gestão de projetos de software que integra DDD e SDD, definindo como projetos são estruturados, documentados e evoluídos — tanto por humanos quanto por agentes de IA.

📋 O que gerencia

Documentação e configuração dos projetos. O código-fonte vive separadamente em ~/Dev/Projects/.

🎯 Objetivo

Padronizar a estrutura, documentação e evolução de projetos de software.

👥 Público-alvo

Humanos e agentes de IA como cidadãos de primeira classe.

🏛️ Paradigma

DDD (Domain-Driven Design) + SDD (Spec-Driven Development) integrados.

Adesão ao DDD

Domain-Driven Design na Factory

🔷 DDD Estratégico (Macro)

ConceitoAplicação na Factory
Bounded ContextCada contexto delimitado tem fronteira explícita e é dono dos seus dados [11].
Context MapMapeamento dos relacionamentos: Customer-Supplier, Conformist, Anti-Corruption Layer, Open Host Service [11].
Linguagem UbíquaTermos compartilhados entre técnicos e negócio, refletidos nas specs [11].

🔶 DDD Tático (Micro)

ConceitoAplicação na Factory
AgregadosUnidades de consistência transacional com raiz (Aggregate Root).
EntidadesObjetos definidos por identidade única (ID), não por atributos.
Value ObjectsObjetos imutáveis definidos por seus valores (ex: Money, Address).
RepositóriosAbstração entre domínio e persistência de dados.

Adesão ao SDD

Spec-Driven Development na Factory

No SDD, cada Bounded Context expõe suas capacidades através de uma especificação formal (spec).

Mapeamento DDD ↔ SDD

A Regra de Ouro

"Os nomes nas specs devem ser idênticos aos nomes da Linguagem Ubíqua do DDD."

🔹 FASE 1: Iniciação

Scaffolding via MyCodebase, definição dos Bounded Contexts iniciais, criação do Context Map.

🔹 FASE 2: Especificação

Criação de specs para cada Bounded Context, validação da Linguagem Ubíqua, templates configurados.

🔹 FASE 3: Desenvolvimento

Implementação orientada pelas specs, agentes de IA atuando, validação contínua spec ↔ implementação.

🔹 FASE 4: Evolução

ADRs para decisões, backlog sincronizado (Factory ↔ MyBacklogManager) [1], documentação via templates.

Fluxo de Trabalho

🔄 Projeto Migrado (Legado)

🔸 FASE 1: Avaliação

Análise do código existente, identificação de domínios e subdomínios implícitos, mapeamento de dependências e acoplamentos.

🔸 FASE 2: Modelagem Reversa

Extração dos Bounded Contexts a partir do código legado, definição da Linguagem Ubíqua com stakeholders, criação do Context Map (como é vs. como deveria ser).

🔸 FASE 3: Contratualização

Criação retroativa de specs por Bounded Context, identificação de gaps (spec vs. implementação real), templates de documentação aplicados ao legado.

🔸 FASE 4: Estabilização

ADRs documentando decisões históricas e novas, integração com MyBacklogManager [1], agentes de IA configurados, plano de evolução para reduzir dívida técnica por contexto.
