What is Domain-Driven Design?

"Tackle complexity at the heart of software by connecting implementation to an evolving model of the core business." — Eric Evans

DDD is a software design philosophy that places the business domain at the center of every decision. Instead of building software around technical concerns, you build it around the language, rules, and mental models of domain experts.

🎯

Primary Goal

Create systems whose design mirrors business reality, making them easier to understand, evolve, and maintain over time.

🤝

Collaboration First

Developers and domain experts work together continuously, refining a shared model that drives both conversation and code.

🧱

Model-Driven

The domain model is not just documentation — it is expressed directly in the code through entities, value objects, and aggregates.

The Three Pillars of DDD

🗣️

Ubiquitous Language

A shared, rigorous vocabulary used by everyone — developers, product owners, business analysts. The same terms appear in conversations, documentation, code, and APIs.

Example: Always say "Order," never "Purchase" or "Sale" interchangeably.

📦

Bounded Context

A boundary within which a specific domain model applies. Each context owns its data and defines its own ubiquitous language, preventing model confusion.

Example: "Customer" in Billing ≠ "Customer" in Support — different attributes, different rules.

🗺️

Context Map

A visual overview of how bounded contexts relate to each other — upstream/downstream, shared kernel, anti-corruption layers, etc.

Example: Orders context is upstream of Shipping; Shipping translates Order events via an anti-corruption layer.

Strategic vs. Tactical DDD

🔭 Strategic Design

Macro level. Decomposes the business into bounded contexts and maps their relationships.

  • Bounded Contexts
  • Context Mapping
  • Subdomains (Core, Supporting, Generic)
  • Anti-Corruption Layers

Answers: "How do we split the system?"

🔬 Tactical Design

Micro level. Implements each bounded context with precise modeling patterns.

  • Entities (identity, lifecycle)
  • Value Objects (immutable, by attributes)
  • Aggregates (transactional consistency boundary)
  • Domain Events, Repositories, Services

Answers: "How do we build each piece?"

Each context has its own model. Here's how the Order Aggregate might look inside the Orders context:

// Orders Bounded Context — Aggregate Root class Order { constructor(id, customerId) { this.id = id; // Entity identity this.customerId = customerId; this.items = []; // Value Objects this.status = "draft"; } addItem(productId, qty, price) { this.items.push(new OrderItem(productId, qty, price)); } submit() { if (this.items.length === 0) throw new Error("Empty order"); this.status = "submitted"; this.addDomainEvent(new OrderSubmitted(this.id)); } }

The aggregate enforces invariants (no empty orders) and raises domain events that other contexts consume.

What is Spec-Driven Development?

SDD is the practice of defining formal, machine-readable specifications for every bounded context before writing implementation code. Each spec serves as a contract that governs how a context behaves and communicates.

📜

Spec = Contract

A specification defines inputs, outputs, validation rules, and side effects — like a typed API contract that is both human-readable and machine-verifiable.

🔒

Isolation by Design

Each bounded context gets its own spec. Teams can work independently because the contract guarantees compatibility at the boundaries.

🤖

AI-Ready

Formal specs enable AI-assisted code generation, automated testing, and validation — the spec becomes the source of truth for both humans and tools.

A typical spec includes:

// Spec for the Payments Bounded Context spec Payments { // Operations processPayment(orderId: UUID, amount: Money) → PaymentResult // Business rules invariant: amount.currency === order.currency invariant: amount.value > 0 // Side effects emits: PaymentProcessed | PaymentFailed // Dependencies requires: PaymentGateway, OrderRepository }

The spec is the single source of truth — implementation, tests, and documentation all derive from it.

The Integration: DDD + SDD

The Factory Framework unifies both methodologies into a cohesive governance model:

DDD

Defines HOW the business is modeled

Bounded contexts, ubiquitous language, aggregates, domain events

SDD

Defines WHAT each context guarantees

Formal contracts, invariants, side effects, dependencies

Core Principles of the Factory Framework

📋 Template-Driven

Documentation and specs derive from standardized templates, ensuring consistency across all contexts.

🔗 Contract-First

Every bounded context exposes a formal spec before implementation begins — no ambiguity at the boundaries.

🔄 Continuous Governance

As the business evolves, specs and models evolve together, keeping the system aligned with reality.

When to Use — Decision Matrix

✅ Recommended When

  • The business domain is complex with many rules and exceptions
  • Multiple teams work on interconnected systems
  • The software must evolve continuously over years
  • You need clear contracts between services or microservices
  • AI-assisted development is part of the roadmap
  • Regulatory compliance requires auditable design decisions

❌ Not Necessary When

  • The application is CRUD-dominant with little business logic
  • There is a single small team with low coordination overhead
  • The project is a short-lived prototype or proof of concept
  • The domain is well-understood and unlikely to change
  • Speed to market outweighs long-term maintainability

The sweet spot: medium-to-large systems with genuine business complexity and multiple teams.
